# 🌊 Industrial Smart Turbidity Node (ESP32)

โหนดตรวจวัดความขุ่นน้ำอัจฉริยะด้วยบอร์ด **ESP32** ออกแบบมาสำหรับงานอุตสาหกรรม (Industrial IoT) รองรับการใช้งานหลายบอร์ดพร้อมกันด้วยโค้ดชุดเดียว (Multi-Node) จัดการการตั้งค่าและอัปเดตเฟิร์มแวร์ไร้สาย (OTA) ผ่าน **GitHub** และส่งข้อมูลขึ้นคลาวด์ **ThingsBoard**

## ⚙️ ฮาร์ดแวร์ที่ใช้
* **Microcontroller:** ESP32 NodeMCU (esp32dev)
* **Shield:** IOXESP32 Modbus RTU Shield
* **Sensor:** DFRobot RS485 Industrial Water Quality Turbidity Sensor 0-1000 NTU (**SEN0710**)
* **การเชื่อมต่อ:** Serial2 (RX = GPIO16, TX = GPIO17), **Baud Rate 4800 8N1** (ค่าจากโรงงานของ SEN0710)
* **สายเซนเซอร์:** น้ำตาล = VCC (10-30V DC) · ดำ = GND · **เหลือง = RS485-A** · **น้ำเงิน = RS485-B**
* **Register:** `0x0000` = ความขุ่น, `0x0001` = อุณหภูมิ (ทั้งคู่ต้อง ÷10), Slave ID = 1, Function code 0x03
* **ไฟเลี้ยง:** เซนเซอร์ใช้ไฟเลี้ยง 12V ร่วมกับชิลด์ (ส่วนบอร์ด ESP32 ใช้ไฟจาก USB/Adpater 5V)

---

## 🛠️ การติดตั้งและใช้งานครั้งแรก

### 1. แฟลชโค้ดและจด MAC Address
1. เปิดโปรเจกต์นี้ด้วย **VS Code + PlatformIO**
2. เสียบสาย USB และกดปุ่ม **Upload (➔)** ที่แถบด้านล่าง
3. เปิด **Serial Monitor (🔌)** เพื่อดู `MAC Address` ของบอร์ด (เช่น `246F287ABC12`) ให้จดค่านี้ไว้

### 2. ตั้งค่าบน GitHub (config.json)
1. ไปที่ไฟล์ `config.json` ใน Repository นี้
2. แก้ไขไฟล์โดยใส่ **MAC Address** ของคุณแทนที่ตัวอย่าง
3. ใส่ **ThingsBoard Token** ของอุปกรณ์
4. กำหนดเวลา **sleep_minutes** (รอบเวลาตื่นมาส่งข้อมูล เช่น 15 นาที)
5. บันทึก (Commit) การเปลี่ยนแปลง

### 3. ตั้งค่า WiFi ให้บอร์ด (ทำเฉพาะครั้งแรกหรือเปลี่ยนสถานที่)
1. เปิดบอร์ด ESP32 มันจะพยายามหา WiFi หากไม่พบจะปล่อย Hotspot ชื่อ **`TurbidityNode_AP`**
2. นำสมาร์ทโฟนเชื่อมต่อ WiFi ชื่อดังกล่าว
3. หน้าเว็บจะเด้งขึ้นมาอัตโนมัติ ให้เลือก WiFi สถานที่ทำงานและใส่รหัสผ่าน
4. บอร์ดจะบันทึกรหัสผ่านไว้ถาวรและเริ่มการทำงานทันที

## 🔄 การทำงานของระบบ (Workflow)
ระบบถูกออกแบบมาให้ประหยัดทรัพยากรและเสถียรที่สุดด้วย FSM และ Deep Sleep โดย **ทุก state จะถูกส่งขึ้น ThingsBoard แบบ real-time**:
1. **WIFI_CONNECT:** เชื่อมต่อ WiFi ที่เคยบันทึกไว้ — ต่อไม่ได้คือไปนอนรอรอบหน้า
2. **SYNC_CONFIG:** โหลด `config.json` จาก GitHub มาอัปเดต Token / เวลา Sleep ตาม MAC ของตัวเอง
   - **ถ้าโหลดไม่สำเร็จ จะใช้ค่าเดิมที่เคย sync ได้แล้วไปต่อ** ไม่ทิ้งค่าวัดทั้งรอบ
3. **MQTT_CONNECT:** ต่อ ThingsBoard แล้วรายงาน เวอร์ชันเฟิร์มแวร์ / สาเหตุการรีบูต / state ที่ค้างครั้งล่าสุด
4. **READ_SENSOR:** อ่านเซนเซอร์ผ่าน Modbus RTU (ลองซ้ำ 3 ครั้งก่อนยอมแพ้)
5. **SEND_TELEMETRY:** ส่งความขุ่น + RSSI + สถานะ — **ส่งเสมอแม้เซนเซอร์อ่านไม่ได้** จะได้รู้จากฝั่งคลาวด์ว่าโหนดยังมีชีวิตแต่เซนเซอร์มีปัญหา
6. **OTA_UPDATE:** ถ้าเจอเวอร์ชันที่ใหม่กว่า จะอัปเดต **หลังส่งข้อมูลเสร็จแล้ว** ค่าวัดรอบนั้นจึงไม่หายไปกับการรีบูต
7. **GO_SLEEP:** ปิด MQTT/WiFi ให้เรียบร้อยแล้วเข้า Deep Sleep ตามเวลาที่ตั้งไว้

## 🛡️ การกู้คืนตัวเองเมื่อบอร์ดค้าง (Watchdog)
โหนดติดตั้งอยู่ไกล เข้าไปกดรีเซ็ตเองไม่ได้ ระบบจึงมีการป้องกัน 3 ชั้น:

| ชั้น | กลไก | ค่าที่ตั้ง |
|------|------|-----------|
| 1 | **Task Watchdog** — ค้างเกินเวลากำหนด = รีเซ็ตบอร์ดทันที | `WDT_TIMEOUT_SECONDS` = 180 วินาที |
| 2 | **Max Awake** — ตื่นนานผิดปกติแต่ยังไม่ค้างสนิท = บังคับไปนอน | `MAX_AWAKE_MS` = 5 นาที |
| 3 | **Boot-loop Guard** — รีเซ็ตผิดปกติติดกันหลายครั้ง = ข้ามรอบไปนอนก่อน | `MAX_CONSECUTIVE_FAULTS` = 3 |

จุดสำคัญ: state ที่กำลังทำอยู่ถูกจดไว้ใน **RTC memory** ซึ่งรอดจากการรีเซ็ต พอบอร์ดตื่นขึ้นมาใหม่มันจะส่ง `last_fault_state` ขึ้น ThingsBoard ให้เรารู้ว่า **มันค้างตรงไหน** โดยไม่ต้องเดินไปดูหน้างาน

ระหว่าง OTA จะมีการป้อน watchdog ตาม progress ของการดาวน์โหลด จึงไม่โดนรีเซ็ตกลางคันตอนเน็ตช้า แต่ถ้าดาวน์โหลดค้างจริงๆ watchdog ก็ยังทำงานอยู่

## 📡 ข้อมูลที่ส่งขึ้น ThingsBoard
ตั้งใจให้ payload เล็กที่สุด — ทุกข้อความมี **4 ค่าพื้นฐานเหมือนกันหมด**

| Key | ความหมาย |
|-----|----------|
| `mac` | MAC Address ของโหนด |
| `state` | state ที่กำลังทำ เช่น `READ_SENSOR`, `OTA_UPDATE`, `GO_SLEEP` |
| `version` | เวอร์ชันเฟิร์มแวร์ที่รันอยู่จริง |
| `sleep` | รอบเวลา Deep Sleep (นาที) ที่ใช้อยู่จริง |

เฉพาะข้อความตอนส่งค่าวัด จะมี 2 ค่านี้เพิ่มเข้ามา

| Key | ความหมาย |
|-----|----------|
| `turbidity` | ความขุ่น หน่วย NTU |
| `temperature` | อุณหภูมิน้ำ หน่วย °C |

**อ่านสถานะผิดปกติจาก key `state` ได้เลย** ไม่ต้องมี key เพิ่ม:
* `SENSOR_ERR_E2` — อ่านเซนเซอร์ไม่ได้ (E2 = ไม่มีการตอบกลับ) และรอบนั้นจะไม่มี `turbidity` ติดมา
* `RECOVERED_FROM_READ_SENSOR` — รอบก่อนบอร์ดค้างที่ state นั้นแล้วโดน watchdog รีเซ็ต
* `OTA_SKIPPED` — พยายาม OTA เวอร์ชันเดิมครบจำนวนครั้งแล้วเลิกลอง

**Attributes** (`v1/devices/me/attributes`) — ส่งชุดเดียวกันซ้ำอีกทาง เพื่อให้เห็นสถานะล่าสุดบนหน้า Device โดยไม่ต้องเปิดกราฟ

> แนะนำให้สร้าง Alarm บน ThingsBoard จาก `state` ที่ขึ้นต้นด้วย `SENSOR_ERR` หรือ `RECOVERED_FROM` เพื่อให้เตือนเมื่อโหนดที่อยู่ไกลมีปัญหา

## 🚀 การทำ OTA Update (อัปเดตโค้ดไร้สาย)
หากต้องการแก้บั๊กหรือเพิ่มฟีเจอร์ให้บอร์ดทุกตัวพร้อมกัน:
1. แก้ไขเลข `#define CURRENT_VERSION` ในไฟล์ `include/app_config.h` ให้สูงขึ้น (เช่น จาก `"1.0.0"` เป็น `"1.0.1"`)
2. กด **Build (✔)** ใน PlatformIO
3. นำไฟล์ `.pio/build/esp32dev/firmware.bin` ไปสร้าง **Release** บน GitHub (ตั้ง Tag ให้ตรงกัน เช่น `v1.0.1`)
4. ขั้นตอนสุดท้าย ไปแก้ไฟล์ `config.json` เป็น `"version": "1.0.1"`
*เมื่อบอร์ดตื่นขึ้นมารอบหน้า มันจะดาวน์โหลดโค้ดใหม่ไปติดตั้งเองอัตโนมัติ!*

**ข้อควรรู้เรื่องเวอร์ชัน**
* ระบบเทียบเวอร์ชันแบบ `major.minor.patch` และจะอัปเดต **เฉพาะเมื่อเวอร์ชันใน `config.json` สูงกว่าตัวที่รันอยู่** เท่านั้น ใส่เลขต่ำกว่าบอร์ดจะไม่ downgrade ให้
* ถ้าพยายาม OTA เวอร์ชันเดิมแล้วล้มเหลวครบ `MAX_OTA_ATTEMPTS` (2 ครั้ง) บอร์ดจะเลิกลองและส่ง state `OTA_SKIPPED` ขึ้น ThingsBoard — กันวนดาวน์โหลดไฟล์ที่ไม่มีอยู่จริงไม่รู้จบ
* ดูความคืบหน้าได้จาก key `state` บน ThingsBoard: จะเห็น `OTA_UPDATE` พร้อมเลขเวอร์ชันปลายทางก่อนบอร์ดรีบูต

## ⚠️ ความปลอดภัยของ Token
`config.json` ถูกโหลดผ่าน `raw.githubusercontent.com` แบบ public หมายความว่า **ThingsBoard Token ในไฟล์นี้ใครก็อ่านได้** ถ้า repo เป็น public ใครที่เห็น token ก็ยิงข้อมูลปลอมเข้า device ได้ ถ้าจะใช้งานจริงจังแนะนำให้เปลี่ยน repo เป็น private แล้วดึงผ่าน token ของ GitHub หรือย้าย token ไปเก็บใน NVS ของบอร์ดแทน (ตอนนี้ `config.json` ในโปรเจกต์ยังมี token จริงอยู่ ควร revoke แล้วออกใหม่)
